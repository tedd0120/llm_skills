# Git 本周 Commit 总结

输出一份简体中文 Markdown 周报，完整覆盖本周一 00:00 至调用时刻的已提交 Git 变更。

## 内容规范

- 将同一主题的连续提交合并，按读者能理解的功能模块组织。
- 只有重大变更独立进入摘要表、模块标题或 bullet。重大变更包括新增核心能力、明显改变用户行为、解决关键故障，以及显著改善安全性、可靠性、性能或交付效率的工作。
- 将依赖升级、配置调整、监控日志、测试维护、小修复、文档维护和内部清理等日常运维合并为一个“日常运维与维护”模块，用 1–2 个 bullet 概括整体结果。
- 优先说明用户、运营者或维护者获得的能力，以及改动解决的具体问题。
- 每项事实以提交差异、代码、测试或文档为依据；无法证实的效果不写。
- Merge commit 与其包含的普通提交只计算一次。
- 自动化测试归入对应能力或质量保障，不单列测试清单。
- 使用通俗表达，让不了解项目的读者无需背景知识也能看懂。
- 省略提交标识、作者、脚本名、函数名、文件名、具体参数名、代码行数、命令和版本控制操作细节。

## 格式规范

- 标题固定为 `# 本周提交变更总结`。
- 标题后立即放置“干了什么 / 解决了什么问题”两列表格，每项重大变更占一行；日常运维合并为一行。
- 表格后用一句话说明时间范围、提交数量和本周主题。
- 正文按重大变更设置模块，并按需增加一个“日常运维与维护”模块；每个模块最多 2 个 bullet。
- 每个 bullet 只表达一个主要结论。
- 若本周没有提交，输出标题和一句简短说明。

```markdown
# 本周提交变更总结

| 干了什么 | 解决了什么问题 |
| --- | --- |
| <概括性动作> | <对应痛点> |

本周一至今共整理 <N> 次提交，主要围绕“<一句话主题>”展开。

## <模块一>

- <结论一>
- <结论二>

## <模块二>

- <结论一>
```

## 交付规范

最终回复只包含周报正文。第一个字符为 `#`，结尾停在报告正文。
