# 双轴审查

> **只回复可改进项**：报告只列需要修改的问题，优点、肯定与无问题的检查过程一律略过。
>
> **直接在对话中回复**：报告作为对话回复输出；全程只读取代码与文档，所有文件保持原样，也不新建报告文件。

## 1. 锁定审查对象

- **代码变更**：
  - 用户指定基准点（分支、tag、commit SHA、`HEAD~N`）时，先用 `git rev-parse <基准点>` 校验引用，再执行 `git diff $(git merge-base <基准点> HEAD)`，它同时包含已提交与未提交的改动；用 `git log <基准点>..HEAD --oneline` 读取提交信息。
  - 未指定基准点且工作区有改动（含未跟踪文件）时，审查 `git diff HEAD`。
  - 以上两种情况都执行 `git status --porcelain`，将 `??` 开头的未跟踪文件整份读取并纳入审查。
  - 工作区干净且未指定基准点时，询问用户比较基准。
- **实施方案**：读取用户指定的计划文件（如 `.work/<任务ID>/plan.md`、设计文档）或对话中的方案，同时读取方案涉及的既有源码与调用链，核实方案假设与仓库现状一致。

## 2. 确定两轴依据

### Spec 依据

按顺序查找，找到即止：

1. 用户提供的需求描述、关联文件或对话中的任务要求。
2. 提交信息引用的 Issue（用 `gh issue view <编号>` 读取）或任务编号。
3. 匹配的 `.work/<任务ID>/plan.md`、`docs/` 或 `specs/` 下的规格文档。
4. 以上均无时询问用户；用户确认没有规格时，`## Spec` 栏只写 `无可用需求规格`。

### Standards 依据

1. **仓库明文规范**：仓库根目录及每个被审查文件所在目录链上的 `AGENTS.md`、`CLAUDE.md` 与它们引用的规范文档，以及根目录的 `CODING_STANDARDS.md`、`CONTRIBUTING.md`。
2. **坏味道基线**：Fowler 定义的 12 项坏味道。以下三项在本 skill 中扩大了范围：
   - `Duplicated Code`：也包括重新实现仓库已有能力或成熟第三方库的功能。
   - `Speculative Generality`：也包括实现内部的兜底分支与防御性错误捕获。
   - `Mysterious Name`：也包括计划阶段与步骤的名称。

   其余九项按原定义：`Feature Envy`、`Data Clumps`、`Primitive Obsession`、`Repeated Switches`、`Shotgun Surgery`、`Divergent Change`、`Message Chains`、`Middle Man`、`Refused Bequest`。

## 3. 逐项审查

### Spec 轴

逐条核对需求依据，每条问题引用需求原文：

- **偏差（Wrong）**：实现或方案与需求原意冲突、只修补症状而遗漏根因、阶段顺序存在依赖倒置。
- **遗漏（Missing）**：需求要求的功能、边界条件、迁移兼容或验证步骤未覆盖。
- **越界（Scope Creep）**：引入需求未要求的功能、对外配置项或无关重构。

### Standards 轴

逐条应用仓库规范与 12 项坏味道，按三条规则裁决：

- 仓库规范明确允许的写法，豁免对应的坏味道。
- 违反仓库规范标 `[硬性违规]` 并注明规范文件与条款；命中坏味道标 `[启发式判断]` 并注明坏味道名称。
- Linter、Formatter、类型检查器已强制的规则交给工具，审查时跳过。

### 两轴分工

同一问题只记入一栏：功能范围的问题归 Spec，实现内部的设计问题归 Standards。

## 4. 输出报告

- 固定用 `## Spec` 与 `## Standards` 两个二级标题分栏。
- 每栏按严重程度排序：Spec 栏依次为偏差、遗漏、越界；Standards 栏中 `[硬性违规]` 排在 `[启发式判断]` 前面。
- 每条格式：``- `<位置>` [类别/性质]：问题描述（依据：<需求原文、规范条款或坏味道名称>） → 改进做法。``代码审查的位置写 `文件路径:行号`，方案审查写计划章节或步骤。
- 某栏没有可改进项时，该标题下只写 `无`。
- 报告末尾附一行汇总，最严重项取各栏排序后的第一条：
  `汇总 — Spec: <N> 项（最严重：<简述或无>） | Standards: <M> 项（最严重：<简述或无>）`
