# GitHub Releases 自动更新方案

交付带证据的自动更新实施方案：每条结论附上仓库文件、命令输出或锁定依赖源码依据，明确改动文件范围与可观察的验收标准。默认交付方案文档；代码实现、凭据配置、提交与发布在用户本次明确授权后执行。

系统由三方协作构成：GitHub Actions 构建并签名产物，GitHub Releases 托管安装包与更新清单，客户端检查、下载、验签并拉起安装器。客户端仅将已正式发布的 Release 视为可安装版本。

## 1. 盘点项目事实

若承接既有计划，先读取对应 `plan.md`。检查工作区状态，标注已有改动的归属。优先使用代码索引定位入口，无索引时使用 `rg` 检索。

| 盘点维度 | 关键证据来源 |
|---|---|
| 桌面宿主与精确版本 | 原生或主进程入口、依赖锁文件（以实际桌面宿主为准） |
| 打包器与安装格式 | 构建脚本、NSIS / MSI / MSIX / DMG / AppImage 配置、已发布资产 |
| 存量用户安装形态 | 应用标识、安装目录、用户级或机器级权限、便携版或商店版、数据目录 |
| 现有更新链路 | 更新命令、真实调用方、事件订阅、后台任务、现有凭据存储位置 |
| 发布边界 | Git remote、仓库归属与公开性、版本真源、标签规则、CI 与更新清单 |
| 运行时约束 | 代理配置、长耗时写入、数据库连接、子进程、退出流程、单实例锁 |

每条结论记为“事实 → 文件或命令证据 → 方案约束”，标注“已确认 / 推断 / 待确认”。组件能力以源码实际调用为准。先完成独立调查，仅在答案会实质改变方案走向时向用户集中提问。

**完成标准：** 完整说明当前安装包如何生成、存量安装如何获得首次更新、程序退出前如何释放资源。

## 2. 选定更新器与分流参考

优先评估项目现有更新器；确需更换时，将安装格式迁移、用户数据保留与首次手动升级计入迁移成本。

| 项目形态 | 首选方案与评估方向 | 框架参考 |
|---|---|---|
| Electron + electron-builder | `electron-updater` | [references/electron.md](references/electron.md) |
| Electron + Forge 或其他打包器 | 对应发行机制自带更新器，同时评估切换打包器的迁移成本 | [references/electron.md](references/electron.md) |
| Tauri | 与项目主版本匹配的 `tauri-plugin-updater` | [references/tauri.md](references/tauri.md) |
| macOS 原生应用 | Sparkle | [references/native.md](references/native.md) |
| .NET、C++、Rust、Python 桌面应用 | Velopack 或现有安装体系配套更新器 | [references/native.md](references/native.md) |
| 应用商店、企业分发或系统包管理器 | 对应分发渠道自带的升级机制 | [references/native.md](references/native.md) |

仅对比当前可达的候选方案，覆盖目标平台、安装格式、锁定版本能力、私有鉴权、签名校验、退出钩子与维护成本。给出唯一推荐方案及核心取舍；与存量安装存在冲突时，单列不兼容点与迁移前提。

**完成标准：** 选定唯一推荐方案并覆盖全部存量安装形态，未决迁移前提已单列；已读取命中分支的框架参考。

## 3. 核查锁定版本契约

读取 [references/release-contract.md](references/release-contract.md)；仓库为私有或由客户端持 Token 访问时，加读 [references/private-releases.md](references/private-releases.md)。

更新签名与操作系统代码签名分别判断。Windows 使用独立更新签名且不强制 Authenticode 的条件，见框架参考与 [发布签名契约](references/release-contract.md#签名要求与-windows-分发)。

对照锁文件中的精确版本查阅官方文档、类型定义与本地依赖源码，输出“能力 / 精确版本 / API 或配置 / 证据位置 / 限制”核查表（附核查日期），逐项回答：

- **请求与代理：** 元数据、清单、安装包分别由哪个 HTTP 客户端发起？代理与鉴权覆盖哪些请求？
- **重定向与安全：** 重定向时如何剥离敏感请求头、如何阻断 HTTPS 降级、错误对象是否保留 HTTP 状态码？
- **超时与取消：** 检查、下载、等待业务收尾的超时分别由谁控制？取消操作能否中止底层任务？
- **验签与退出：** 下载产物如何落盘保留？何时校验更新签名与系统代码签名？安装前在哪个钩子释放资源？
- **版本一致性：** 应用内版本、Git 标签、更新清单版本与目标架构如何绑定在同一 Release 下？

**完成标准：** 表中每项关键行为均绑定锁定版本的源码或文档证据；本地无法查证的行为全部标为“待验证”。

## 4. 编写方案与交付

将上述结论汇入方案文档，输出路径按优先级取：用户指定路径 → 目标项目任务工作区 `.work/<任务ID>/plan.md` → `data/github-release-updater/<时间_主题>/plan.md`。章节可按目标项目文档结构合并，完整覆盖以下八块：

1. **项目事实与范围：** 目标程序、平台架构、安装格式、存量版本、仓库公开性及工作区既有改动归属。
2. **推荐方案与职责：** 更新器选型依据、Actions / Releases / 客户端三方职责边界、存量用户首次升级路径。
3. **技术契约：** 第 3 步核查表、请求与重定向链路、同一 Release 绑定规则、版本与签名校验；私有仓库补充凭据来源、最小权限、系统凭据库存储及界面保存/替换/清除状态。
4. **交互与异常恢复：** 启动检查、定时检查、手动检查、下载进度、安装确认、关闭窗口与取消任务；逐一定义未配 Token、Token 失效、触发限流、网络或代理失败、产物缺失、验签失败、等待超时、安装器拉起失败时的用户提示与恢复动作。
5. **安装与数据保护：** 安装目录与权限（用户级 / 机器级 / UAC）、应用标识、暂停业务写入的条件与等待上限、退出前清理钩子、数据迁移备份及回退路径。
6. **CI 与发布流水线：** 干净环境构建顺序、版本真源、构建矩阵、Secrets 隔离、更新签名与系统代码签名、草稿上传、远端字节与签名校验、正式发布条件及失败重试策略。
7. **文件改动范围：** 按实际文件路径列出新增、修改、删除职责，复用既有设置、组件与凭据存储；删除接口或权限时附上调用方核查结论。
8. **验收矩阵与执行状态：** 列出风险项、验证方法、预期结果与所属验收层级（静态核对 / 协议测试 / 真实检查 / 真实下载 / 真实跨版本升级），将“计划执行的检查”与“已取得的证据”分列；用 `[ ] 未开始`、`[~] 进行中`、`[x] 完成` 跟踪阶段与任务状态，单列阻塞项与待授权操作。

用户已授权实施时，按方案推进代码实现并实时更新 `plan.md` 进度。

**完成标准：** 方案覆盖上述八块且每项需求均绑定文件路径与可观察验收标准；向用户汇报推荐方案、方案文件路径、前置条件及当前达到的验收层级（Token 创建、密钥上传、标签推送与 Release 发布留待用户执行或显式授权）。
