# 项目内按需 runner

仅在用户选择本地 runner 时读取。GitHub Actions 调度本机测试与打包，云端使用同一次构建产物完成干净安装验收和正式发布。结合 [发布契约](release-contract.md) 执行。

## 部署到目标项目

1. 核实目标仓库、平台、架构、工具链、网络和仓库 runner 管理权限。使用目标项目自身的名称与标签，按已授权范围注册；临时注册 token 仅用于配置，不写入文档、源码或日志。
2. 从 GitHub 官方来源取得适配平台的 runner，记录版本并核验官方摘要。安装到目标项目忽略目录，例如 `.local/github-runner/`；独立 checkout 放其 `_work/`，下载缓存放其 `state/`。确认这些目录与注册凭据不会进入 Git。
3. 默认注册为当前仓库专用 runner。个人账号下的多个仓库各自注册实例；组织级共享 runner 仅在用户选择共享时配置允许访问的仓库和 runner group。每个实例使用独立工作目录，workflow 使用项目专用标签选择实例。
4. 在目标项目交付按需启动入口，例如 Windows 的 `scripts/start-release-runner.ps1`。从脚本位置解析项目根，隐藏启动；按可执行文件绝对路径核对已有进程，避免重复启动或终止其他实例。验证真实 Listener 和 GitHub online 状态后才触发构建。
5. 为每次任务隔离 profile、临时目录、应用数据和测试 agent 数据；npm、Electron、打包工具等下载缓存可在 runner 专属目录持久复用。Windows 路径使用 `Join-Path` 等原生接口构造。固定工具链版本和测试依赖，避免复用个人安装及凭据。同一用户下的目录和环境隔离不构成账户安全边界。

本地 runner 只接收已授权的受信发布代码。公开仓库的外部 PR 和 fork 任务使用托管 runner，避免把它们调度到开发者主机。构建 job 使用所需的只读仓库权限，发布写权限只授予云端发布 job；签名凭据按发布契约限制到实际签名步骤。

## 单任务运行契约

默认不安装常驻服务或开机启动项。启动入口必须让 runner 完成一个本机 job 后退出，并支持下一次发布时再次启动；失败和取消也要验证退出行为。

部署时核查当前 runner 的官方文档与锁定版本源码。2026-11-13 核查的 runner 2.338.2 支持 `run.cmd --once`，完成一个 job 后退出并保留普通注册，但官方源码已标记此选项将弃用。使用时记录此限制，并在 runner 升级后重新验证。若采用官方 ephemeral 模式，则把每次注册纳入自动发布入口，完成 job 后重新注册的职责由代理承担。仅实现当前选定的一种模式。

启动入口发现配置缺失、注册失效或版本不再支持所选模式时，应给出明确错误。代理按已有授权处理重新注册；不得将启动失败报告为已在线。一次启动仅接一个 job，多平台或多个本机 job 须分别配置兼容实例和启动次数。

## 构建与云端验收分工

- **本机 job：** 独立 checkout 指定 SHA，准备版本，安装锁定依赖，执行类型检查、完整测试、打包及依赖构建目录的专项检查；签名按项目配置执行。保留既有检查覆盖。
- **产物交接：** 上传目标框架要求的完整资产集合及构建清单。清单绑定提交 SHA、版本、平台、架构、run ID、尝试编号、文件名、大小和摘要。资产集合按项目确定，不照搬某个应用的固定四附件。
- **云端 job：** 依赖本机 job 成功，checkout 同一 SHA，下载该次构建产物，核对版本与清单、实际字节及所需签名后执行干净安装、真实旧版升级和数据保留检查，再发布同一个包。云端不重新打包；发布前再次核验产物。
- **失败与重跑：** 任一步失败阻止正式发布。保留原有并发、标签和提交校验。若 artifact 绑定尝试编号，文档明确重跑所有相关 job，避免仅重跑云端时读取前次尝试的包。与已发布同 SHA 的幂等处理保持一致。

## 接入代理发布流程

将下列步骤写入目标项目发布文档，并从 `AGENTS.md` 添加简短触发指针。用户以后要求发布时，由代理执行完整流程，无需用户手动启动 runner：

1. 完成发布预检，检查当前实例是否已有任务。已有任务时跟进至结束；核实归属后处理空闲残留实例。
2. 在已授权的 push、dispatch 或重跑前调用项目启动入口，记录本次启动的进程身份，确认 runner online。未达到在线条件时停止触发并报告原因。
3. 触发后关联目标 SHA、run 与本机 job，跟进构建和云端发布。GitHub workflow 本身无法唤醒已停止的本地进程，此启动步骤由能访问本机的代理或本机发布入口执行。
4. 本机 job 结束后确认 Listener、Worker 和本次启动器退出，普通注册在 GitHub 显示 offline，ephemeral 注册则确认已移除；云端仍需跟进至正式发布成功或明确失败。若触发失败或任务未分配，核实本次启动实例空闲后清理，避免留下监听进程。忙碌或归属无法确认时不终止。

注册和下载缓存可以保留。清理临时文件前核实绝对路径及链接目标属于本任务，避免触碰开发工作区和个人数据。

## 验收与交付

交付启动入口、workflow 分工、发布文档和 agent 指针，并提供以下证据；未执行的真实操作标为待验收：

- 本地实例仅绑定选定范围，独立目录和缓存配置生效；重复启动不产生第二个实例。
- 真实测试与打包成功，云端安装的是同 SHA、同版本、同次构建的包；篡改或错配产物会阻止发布。
- 成功、失败或取消时的退出符合单任务契约；至少实测一个真实本机 job 结束后进程消失及对应注册状态，并验证再次按需启动。
- 云端安装升级与发布检查通过。分别记录测试、打包、上传和云端验收耗时，明确缓存及硬件条件，不预先承诺提速倍数。
