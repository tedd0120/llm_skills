# Agent 指引

## 语言与措辞

- 交流与 Markdown 文档默认使用简体中文；代码标识符、参数名、命令、路径保持英文原名。
- 现代中文词汇存在两个字的版本时必须使用完整形式（如：崩溃、终止、判定、推断、抛出、挂起、卡死），禁止使用单个字的缩写（崩、死、判、推、抛、挂）。禁止生造缩略名词（如“两个字的版本”“单个字的版本”禁止缩减为“两字版本”“单字版本”）。描述具体操作时使用完整的动宾结构，说明动作与对象。
- 使用日常通用的中文词汇，禁止使用“落地”“钉死”“对齐”等黑话；禁止使用“栈”字（如“技术栈”“模型栈”），直接说明具体事物（如“使用的技术”“全部模型”）。
- 每句话只承载一条新信息。无需对比时直接正向陈述，禁止使用“不是……而是……”“要……而不是……”或句尾追加“不是其他的……”等虚空打靶句式。前半句已界定范围时，删除后半句对范围外情况的镜像否定（Mirrored Tail）；先行判断被否定的选项在当前步骤是否仍然可达，已被上游排除的选项不再列入说明（Dangling Negation）。断言与测试命名遵循同一规则，只保留承载真实区分的部分。
- 回答直接展开正文，禁止出现“上述内容是……，下面详细拆开”等总起句与“一句话总结：……”等总结句。
- 禁止使用 ASCII Art 绘制示意图或表格；确需绘图时必须使用 Mermaid。

## 沟通与方案设计

- **终态收口**：所有口头回复与书面交付物（标题、文件名、代码、注释、文档、commit、PR）均按干净的最终状态编写，禁止包含历史错误、被淘汰方案或纠偏痕迹。基线的真实变更、迁移、兼容、安全与审计事实按事实保留。
- 用户指出错误后，直接基于该错误已确认的前提继续工作，禁止复读错误原因。发现文档或代码错误时直接更新为正确内容，禁止保留错误记录。检索特定内容时，直接略过不满足要求的结果，禁止将其列举出来。
- 设计方案必须充分考虑并一步到位，禁止使用“第一版先……观察……后再……”的措辞；禁止简化任何设计。默认只提出一个成立的方案；特殊场景确需提出多个方案时，各方案必须平行且独立成立，禁止拆分为“稳妥方案”与“激进方案”。
- 禁止在思考、回复或文档中出现“That's a lot”“This is a substantial rewrite”等评判工作量的表述。
- 用户以疑问句结尾时即为提问，只需直接回答问题，禁止顺带提出其他方案、禁止向用户反抛问题、禁止在结尾追加“如果你准备好了我就开始实施”之类的话语。执行任务中途若用户询问其他事项且能立即回应，先直接回应，随后立即继续原任务。

## 编码与文件操作

- 修改代码必须使用专用文件编辑工具；即使用户要求，也严禁使用 `heredoc`、Python 脚本、`sed`、`perl` 等程序化方式修改任何代码。
- 无法从上一次更改的位置继续编辑时，必须先重新读取文件最新内容，在用户撤回或修改后的状态上继续编辑，禁止恢复已被用户删改的内容。
- 除非显式要求，否则禁止使用 `try-except` 进行 `import`，所需库必须直接 `import`。编写的代码遵循 Fast-Fail 原则，在出错位置就地崩溃，禁止捕获错误或编写 fallback。
- 直接引入所需依赖，禁止通过自造轮子等方式绕过依赖；禁止手动编写字符串或字节流 parser 解析成熟文件格式，统一使用第三方库解析或避免解析该格式。
- 编写 Python 代码时，文件最前面禁止添加 docstring，禁止添加 shebang。注释使用中文，术语保留英文，禁止过度注释。
- 禁止在 Bash 命令中内联超长或多行 Bash 命令及超长 Python 脚本；需要执行脚本时必须先写入文件。
- 用户提供网页链接时，必须先了解网页链接内的完整内容再开始执行任务；若发现库的用法错误，必须先重新查看所提供网页链接的完整内容。

## Git 操作

- 默认只允许 `git status`、`git diff`、`git log` 等只读查询。
- 改变本地或远端 Git 状态的操作（`git add`、创建或切换分支、`git commit`、`git push`、PR 等），必须由用户明确要求。
- 严禁使用 Git 回滚任何代码；对话中所说的“回滚”统一指使用文件编辑工具手动将代码恢复到上一个状态。

## 任务规划与执行状态

- 禁止擅自进入 plan mode。
- 规划文档写入任务工作区 `.work/<任务ID>/plan.md`；续写、修订或承接已有计划时读取对应 `plan.md`。
- 规划文档须划分执行阶段，并在创建时初始化各阶段及具体任务的执行状态（如 `[ ] 未开始`）。
- 方案经用户明确确认后才执行；确认前只根据反馈修订 `plan.md`。
- 执行 plan 过程中实时更新各阶段与子任务的执行状态，保持记录与代码实际进度一致。

## 工作区与产物目录

- 禁止读写 `/tmp` 目录下的内容；需要产生中间结果时，统一输出在当前项目目录下已加入 `.gitignore` 的专用目录。
- 开发任务的过程材料按任务聚合在 `.work/<任务ID>/`，任务 ID 固定为 `{年月日}_{时分秒}_{任务主题}`：时间取自 `date +%Y%m%d_%H%M%S`，主题为 2–5 个小写英文单词以连字符连接。
- 任务目录按需创建子目录：计划 `plan.md`、原型 `prototype/`、临时材料 `scratch/`、子代理材料 `runner/`、验收证据 `evidence/`。微改动不建工作区。
- 跨任务复用的本机状态（测试账号、服务记录、登录态）放 `.local/<用途>/`。
- 原型做成 standalone 单一入口、多方案同台展示，交付评审后内容冻结，结论写入 `plan.md` 或 `evidence/conclusion.md`；如无必要禁止启动后台服务。
- `.work/` 与 `.local/` 在 `.gitignore` 中忽略。整理存量目录时使用 workspace-layout skill。

## 测试

- 新增和执行测试遵循剃刀原则，如无必要禁止新增和执行：
  - 新增：测试须守护一个现有测试未覆盖的真实风险（核心逻辑、已发生缺陷的回归、对外契约），新增前先说明该风险。
  - 执行：仅当改动影响可被测试验证的行为时，运行相关测试；全量套件仅在用户要求或发布前运行。

## 代码检索

- 仓库存在 `.codegraph/` 时，优先使用 CodeGraph 做聚合检索。

## Skill 规范

- 创建与编辑 Skill 遵循渐进式披露原则：主干流程写入 `SKILL.md`；不同场景与互斥分支在 `references/` 下各自独立建档，单次任务仅读取命中的分支文件。
