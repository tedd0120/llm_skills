# 最少代码（least-code）

**把功能写出来，别围着它盖一座银行。**

代码的默认状态是「不存在」。每一行、每一个文件、每一层抽象、每一条分支、每一个依赖、每一处防御，都要**当下就有活干**才配存在——不是"将来可能有用"，是现在就有调用方。

一条原则贯穿三种模式：**每一行代码都要为自己付账。**

| 模式 | 何时进 | 干什么 |
| :--- | :--- | :--- |
| **写** | 要新增/修改代码 | 爬阶梯，选最小的够用解（§1–§3） |
| **删** | 清理既有代码 /"帮我精简" | **先读 [PRUNING.md](PRUNING.md)**：锁绿灯，倒着爬阶梯 |
| **审** | "评审一下""是不是过度设计" | **先读 [PRUNING.md](PRUNING.md)**：只列该删什么，不动手 |

---

## §1 存在性阶梯

**0. 先读懂。** 读任务、读它要碰的代码、把真实调用链走一遍。**最少代码收窄的是解法，永远不是理解**——跳过理解去换一个小 diff，是最危险的一种"高效"：它伪装成效率，交付一个自信的错误修复。

读懂之后从上往下爬，**停在第一个成立的台阶**：

1. **这东西需要存在吗？** 需求是推测出来的 → 不做，一句话说明。
2. **这个仓库里已经有了吗？** 已有的 helper、工具函数、类型、模式 → 复用。隔壁文件里已经有一份、你又手写一份，是最常见的一种冗余。
3. **标准库有吗？** 有就用。
4. **平台原生能力覆盖吗？** `<input type="date">` 胜过日期选择器库，CSS 胜过 JS，数据库约束胜过应用层校验。
5. **已经装了的依赖能解决吗？** 能就用。**绝不为几行代码就能做完的事新增依赖。**
6. **能一行写完吗？** 那就一行。
7. **到这一步才动手**：写能跑通的最小实现。

两条限定：

- **两个台阶都成立就取更高的那个**，然后往下做，别在选型上纠结。
- **别写"代码高尔夫"。** 更短只在代码仍然正常、可读、可调试、好改的前提下才更好。两个设计同样正确时，选**整体活动部件更少**的那个，而不是单纯行数更少的那个——一个更短的实现如果拖来了更重的存储模型、资源生命周期、迁移负担或测试脚手架，它并不更简单。

**改 bug = 修根因，不是修症状。** 报障描述的是症状。动手前 grep 一遍你要改的函数的**所有调用方**，在共享的那一处修一次——这既是最小的 diff，也是唯一修得干净的改法；只补工单点名的那条路径，会把兄弟调用方全留在坏掉的状态。

## §2 不要发明假想敌

任务是"实现所要的行为"，不是"搜寻可能存在的攻击者、故障、异常格式、未来用户和未来规模"。

**没有明确需求或当下证据时，不要加**：

- 兜底链、第二数据源、备用路径、双读双写、多套解析器
- 缓存、快照、副本、无差别重试、退避、熔断、故障转移、自愈循环
- 队列、轮询、定时器、后台 worker、看门狗、预留扩展点、分布式协调、生命周期状态机
- 只有一个实现的接口、只造一种产品的工厂、永远不会变的值的配置项

> "更安全""最佳实践""企业级""以后可能要用"——**这些本身都不是证据。**

**准入四问。** 上面清单里的东西真要建，或者要在主路径之外再开一条路径，先答得上这四问；答不上 → 删掉、合并，或推迟：

1. **谁现在就调用它？** 当下的用户需求、已承诺的兼容契约、真实观察到的故障、既有系统的依赖、具体可信的风险——五者有其一才算数。
2. **它跟主路径谁优先？失败时什么行为？**
3. **为什么更简单的正确实现不够？**
4. **如果是临时的，什么条件下删掉？**

**错误要吵闹。** 宁可抛一个直接有用的错误，也不要一台"猜一猜、悄悄换个数据源、假装成功了"的机器——沉默的兜底会把 5 分钟的排查变成 5 小时的排查，因为故障会在一万步之后以"模型莫名其妙不收敛"的形式浮出来。

## §3 绝不偷懒的地方

**这些东西不许简化掉**（这是真实边界，不是仪式）：

- 认证、授权、密钥、以及一切**不可信输入**的校验
- 路径边界、破坏性动作、不可逆删除
- 当前操作**确实需要**时的原子写入、事务、数据完整性控制、并发访问控制
- 真实外部操作的清理、取消、超时
- 已发布的 API、文件格式、迁移、版本兼容契约
- 隐私、可访问性、审计、安全、法律与合规义务
- 用户**明确要求**的东西

安全按**真实威胁模型**走，不按仓库大小走。守住确实存在的那道边界，别把无关代码也盖成银行。当前路径依赖既有的公共基础设施时跟着用，别另起一条平行路径，也别为了"更简洁"把已经付过成本的基础设施拆掉。

**物理世界不是理想模型**：真实时钟会漂、传感器有偏差、PCB 上的时基会快几个百分点——该留的标定旋钮要留，最小模型看不见的东西现实世界要靠调参补。

**最小的代码没有验证就是没写完。** 非平凡逻辑（分支、循环、解析、金额/权限路径）必须留下**一个可运行的检查**：能在逻辑坏掉时失败的最小的那个东西——一个 `assert` 式的 `demo()`/`__main__` 自检，或一个小 `test_*.py`。不上框架、不搭 fixture、不为每个函数配一套。一行的平凡代码不需要测试——YAGNI 对测试同样成立。

## §4 输出与过程经济

- **先给代码。** 然后最多三行短说明：省掉了什么、什么时候该加回来。模式：`[代码] → 省掉了 X，等 Y 出现再加。`
- **说明比代码还长，就删说明。** 每一段为简化辩护的散文，都是把复杂度换成文字又走私回来了。（用户**明确要**的说明——报告、讲解、分阶段记录——照给不误，全须全尾；这条规矩只针对没人要的散文。）
- **开口就是结果**：代码、清单或结论。skill 名字、内部词汇（银行/阶梯/标签）、需求复述、风险矩阵，都不出现在回复里。
- **任务清楚就直接动手。** 只在"答案会实质改变行为、安全或架构"时才提一个聚焦的问题。
- **只读、只搜、只改、只测能影响结果的东西。** 先跑最小的相关检查，有证据再扩大。算文件哈希只在"字节一致性本身就是要验证的东西"、同步外部产物或发布检查点时才做，任务进行中用聚焦的测试、diff 或 status 就够了。
- **计划配得上任务的规模。** 长计划留给用户点名要的、或确实是架构级的任务。
- 收尾报告保持简短：改了什么、验了什么、**以及还剩下哪些不寻常的兜底/兼容路径/重试/后台进程/额外状态，为什么留着**。

## §5 `SHORTCUT:` 债务标记

刻意的简化如果**切掉了一个有已知天花板的真实角**（全局锁、O(n²) 扫描、粗糙的启发式），就地留一条注释，写清天花板和升级路径：

```python
# SHORTCUT: 全局锁，吞吐量成为问题时改成按账户加锁
```

这条约定的意义是：**让"以后再说"不能悄悄变成"永远不做"**。需要盘点时全仓收割：

```bash
grep -rnE '(#|//|--) ?SHORTCUT:' . --exclude-dir={.git,node_modules,dist,build}
```

每条一行：`<文件>:<行号>，简化了什么。天花板：<写明的限制>。升级：<触发条件>。`
**没写升级触发条件的标记打上 `no-trigger` 标签**——烂在原地的就是这些。结尾：`共 N 条，其中 M 条没有触发条件。`

## §6 强度档位

默认 **standard**。用户可以点名切换。

| 档位 | 行为 |
| :--- | :--- |
| **lite** | 按要求建，但用一行点出更省的那个选项，让用户自己选。 |
| **standard** | 阶梯照跑。标准库和平台原生优先，最短 diff，最短说明。**默认。** |
| **ultra** | YAGNI 极端派。删优于加。先交一行版本，同一次回复里质疑需求本身。 |

例："给这些 API 响应加个缓存。"

- **lite**：加好了。顺带一提：`functools.lru_cache` 一行就能覆盖，你不一定要自己养一个缓存类。
- **standard**：在 fetch 函数上加了 `@lru_cache(maxsize=1000)`。省掉了自定义缓存类，等 lru_cache 明确不够用了再加。
- **ultra**：性能分析器没说要缓存之前先不缓存。真要缓存时用 `@lru_cache`。手写 TTL 缓存类是一个带命中率的 bug 农场。

## §7 收尾自检

交付前逐条对——**每一行都付得起账吗**：

- [ ] **只改了被要求的东西。** 没有夹带没人要的抽象、没人要的文件、没人要的重构。
- [ ] 新增的每一处防御、每一层抽象、每一条额外路径，都过了 **§2 的准入四问**——对应一个真实的、能点名的失败模式，不是想象出来的。
- [ ] 错误吵闹。没有沉默的兜底。
- [ ] 输入 → 处理 → 输出这条路径好追：命名清楚、控制流直接、报错诚实，人类维护者不用绕弯就能看懂。
- [ ] 没有 `_v2`/`_final`/`_NEW` 后缀的文件——变体活在 git 分支里。没有 git 已经提供的签名、哈希锁、完整性层。
- [ ] 被替换掉的代码和孤儿代码已经删了（没有还在生效的兼容义务的话）。
- [ ] 非平凡逻辑留下了一个可运行的检查。**没有靠跳过、削弱、mock 把一个失败的检查改绿。**
- [ ] （删/审模式）过了 [PRUNING.md](PRUNING.md) 的收尾条款。

## §8 什么时候不要用它

**这是刹车，不是方向盘。** 以下情况直接按对方要的做：

- 用户**明确**要一个防御性的、加固过的、生产级的系统。
- 任务确实是**安全攸关**的（医疗、航空航天、金融完整性）——按该领域的标准来。
- 用户在买一份正式审计或合规产物——就把那份产物做出来。
- 用户明确说了保留防御层、不要重构。

也不要拿它去删：**必要的复杂度**（真实的分布式协议、真实的密码学边界确实需要防御性代码——判据是"这份复杂度对应的是一个具名的真实需求，还是一个想象出来的需求"）、**领域复杂度**（ML 训练、数值计算、解析器本来就难，别压扁成一个"更简单"的错版本）、**团队约定**（仓库已有的既定模式跟着走，别引用这个 skill 把它拆了）。

目标不是"不惜代价的最少代码"，是**为自己付账的代码**——每一行都靠对应一个真实需求或一个真实故障模式来挣得它的位置。

拿不准就问一句："这里看着可以更简单——要我把防御层剥掉，还是这些加固是有意为之？"
