# 最少代码（least-code）

**把功能写出来，别围着它盖一座银行。**

代码的默认状态是「不存在」。每一行、每一个文件、每一层抽象、每一条分支、每一个依赖、每一处防御，都要**当下就有活干**才配存在——不是"将来可能有用"，是现在就有调用方。

这个 skill 有三种模式，共用同一条原则：**每一行代码都要为自己付账。**

| 模式 | 何时进 | 干什么 |
| :--- | :--- | :--- |
| **写** | 要新增/修改代码 | 爬阶梯，选最小的够用解（§1–§3） |
| **删** | 清理既有代码 / "帮我精简" | 先锁行为，再按类删（§4） |
| **审** | "评审一下""是不是过度设计" | 只列该删什么，不动手（§5） |

---

## §1 存在性阶梯

写任何代码前，从上往下爬，**停在第一个成立的台阶**：

1. **这东西需要存在吗？** 需求是推测出来的 → 不做，一句话说明。
2. **这个仓库里已经有了吗？** 已有的 helper、工具函数、类型、模式 → 复用。隔壁文件里已经有一份、你又手写一份，是最常见的一种冗余。
3. **标准库有吗？** 有就用。
4. **平台原生能力覆盖吗？** `<input type="date">` 胜过日期选择器库，CSS 胜过 JS，数据库约束胜过应用层校验。
5. **已经装了的依赖能解决吗？** 能就用。**绝不为几行代码就能做完的事新增依赖。**
6. **能一行写完吗？** 那就一行。
7. **到这一步才动手**：写能跑通的最小实现。

三条限定：

- **阶梯跑在理解之后，不是代替理解。** 先读任务、读它要碰的代码、把真实调用链走一遍，再爬阶梯。
- **两个台阶都成立就取更高的那个**，然后往下做，别在选型上纠结。
- **别写"代码高尔夫"。** 更短只在代码仍然正常、可读、可调试、好改的前提下才更好。两个设计同样正确时，选**整体活动部件更少**的那个，而不是单纯行数更少的那个——一个更短的实现如果拖来了更重的存储模型、资源生命周期、迁移负担或测试脚手架，它并不更简单。

**改 bug = 修根因，不是修症状。** 报障描述的是症状。动手前 grep 一遍你要改的函数的**所有调用方**，在共享的那一处修一次——这既是最小的 diff，也是唯一修得干净的改法；只补工单点名的那条路径，会把兄弟调用方全留在坏掉的状态。

## §2 不要发明假想敌

任务是"实现所要的行为"，不是"搜寻可能存在的攻击者、故障、异常格式、未来用户和未来规模"。

**没有明确需求或当下证据时，不要加**：

- 兜底链、第二数据源、备用路径、双读双写、多套解析器
- 缓存、快照、副本、无差别重试、退避、熔断、故障转移、自愈循环
- 队列、轮询、定时器、后台 worker、看门狗、预留扩展点、分布式协调、生命周期状态机
- 只有一个实现的接口、只造一种产品的工厂、永远不会变的值的配置项

> "更安全""最佳实践""企业级""以后可能要用"——**这些本身都不是证据。**

**第二条路径的准入条件**：当下的用户需求、已承诺的兼容契约、真实观察到的故障、既有系统的依赖，或具体可信的风险。四者有其一才建。建的时候必须同时写清楚四件事：**谁调用它、优先级如何、失败时什么行为、如果是临时的，什么条件下删掉。**

宁可抛一个直接有用的错误，也不要一台"猜一猜、悄悄换个数据源、假装成功了"的机器。开发期你要的是**错误吵闹**，不是错误安静：沉默的兜底会把 5 分钟的排查变成 5 小时的排查，因为故障会在一万步之后以"模型莫名其妙不收敛"的形式浮出来。

## §3 绝不偷懒的地方

**最少代码收窄的是解法，永远不是理解。** 跳过理解去换一个小 diff，是最危险的一种"高效"——它伪装成效率，交付一个自信的错误修复。先读透，再偷懒。

**这些东西不许简化掉**（这是真实边界，不是仪式）：

- 认证、授权、密钥、以及一切**不可信输入**的校验
- 路径边界、破坏性动作、不可逆删除
- 当前操作**确实需要**时的原子写入、事务、数据完整性控制、并发访问控制
- 真实外部操作的清理、取消、超时
- 已发布的 API、文件格式、迁移、版本兼容契约
- 隐私、可访问性、审计、安全、法律与合规义务
- 用户**明确要求**的东西

安全按**真实威胁模型**走，不按仓库大小走。守住确实存在的那道边界，别把无关代码也盖成银行。当前路径依赖既有的公共基础设施时跟着用，别另起一条平行路径，也别为了"更简洁"把已经付过成本的基础设施拆掉。

**物理世界不是理想模型**：真实时钟会漂、真实传感器有偏差、PCB 上的时基会快几个百分点。该留的标定旋钮要留——最小模型看不见的东西，现实世界要靠调参补。

**最小的代码没有验证就是没写完。** 非平凡逻辑（分支、循环、解析、金额/权限路径）必须留下**一个可运行的检查**：能在逻辑坏掉时失败的最小的那个东西——一个 `assert` 式的 `demo()`/`__main__` 自检，或一个小 `test_*.py`。不上框架、不搭 fixture、不为每个函数配一套。一行的平凡代码不需要测试——YAGNI 对测试同样成立。

## §4 删模式：安全删除纪律

### 4.1 先锁行为（不可跳过）

**删掉任何一行之前**，先用绿灯测试把行为钉住。对每个要动的文件：找出它的公开/可观测行为（导出函数、handler、CLI 命令）；没有覆盖或覆盖很弱的，**先写最窄的回归测试把当前行为钉住**，跑绿，再开始清理。

建立不了绿灯基线（测试跑不起来）→ **停下来报告**，不要凭感觉删。
**一份清单不等于安全，一个通过的回归测试才是。**

### 4.2 先跑删除阶梯，再做细粒度分析

对每个改动单元，按"最大且最安全的删除优先"依次问：

1. **整个删掉** — 这个行为压根不需要（推测性的、生下来就是死的）。
2. **复用** — 仓库里已有的 helper/模式就能做。
3. **平台/标准库/已装依赖** — 手写日期选择器 → `<input type="date">`；手写查询串解析 → `URLSearchParams`；手写防抖 → 已经 import 的那个工具。
4. **就地简化** — 它必须存在，那就让它更小。

**只有落到第 4 档的代码，才需要往下做逐类分析。** 一个函数被一句平台调用取代，比任何逐行清理都更大、更安全。

### 4.3 什么算冗余

- **判据**：一个强的资深工程师在这个代码库里从零写这个文件，会写出这一行吗？不会 → 是冗余。
- **反矫枉过正判据**：删掉它会改变行为或抹掉意图吗？会 → 留着。

按这个顺序处理（**从最安全到最危险**）：注释 → 死代码 → 防御性代码 → 重复 → 复杂度 → 抽象 → 命名 → 兼容层 → 测试。

**注释与文档** — 复述下一行的旁白注释（`// 计数器加一` 压在 `counter++` 上）、`// ===== HELPERS =====` 之类的分隔条、注释掉的代码、只写了文件名的文件头、重复签名的空洞 docstring、含糊的 TODO、遗留的 `console.log`/`print` → 删。
_留_：解释**为什么**的注释（业务规则、边界情况、绕坑说明、工单链接、正则/算法解释）、BDD 标记。

**死代码与重复** — 未使用的 import、没人调的私有函数、不可达分支、过期的 feature flag、穷尽 return 之后的 `else` → 删。仓库里已有一份的工具被重写了一遍 → 先 `rg` 搜，用已有的那份，哪怕你会写得不一样。
_留_：通过反射/动态派发/字符串查表引用的代码；feature flag 的回滚路径（要跟用户确认）。**偶然的重复**——两段长得像但意图不同、将来会分叉的代码——宁可放着，也别硬抽成一个早产的公共抽象。

**防御性代码** — 对保证非空的值做判空、对静态类型参数做 `isinstance`、必填参数给默认值、同一件事在多层重复校验 → **在信任边界之内**删。`x !== null && x !== undefined && x !== ''` → 收成一个 `if x:`。裸 `except Exception` / 空 `catch {}` → 收窄到具体异常，或加类型判断后把未知异常重新抛出。
_留_：系统边界上的校验（用户输入、HTTP、文件、环境变量、外部 API）、I/O 错误处理、可空的数据库字段、顶层边界的兜底 catch（CLI `main()`、HTTP handler）配日志 + 重抛。
> ⚠️ **删掉一个可达的"吞异常"就是改行为**（原本拿到默认值的输入现在会抛错）——标出来，别直接改。只有当被包住的代码可证明不会抛时才删 catch。**删信任边界上的任何一道防护之前，先写一个对抗性回归测试**（畸形/恶意输入），确认这道防护拿掉就会失败。没有这个测试 → 防护留着。**没被证明冗余的防护，就是承重的。**

**复杂度** — 嵌套超过 3 层 → 卫语句 / 提前返回。一个函数干很多件事（50 行以上、圈复杂度 10 以上是信号）→ 按职责拆。参数超过 5 个且没有结构体 → 打包。4 个以上谓词的布尔表达式 → 给子条件命名或拆开。用 `if/elif` 链做类型/枚举判别 → 换成 `match/case` + 通配分支上 `assert_never`。
_这些数字是信号，不是红线。_ 代码库既有的复杂模式、性能热点路径 → 留着。

**多余的抽象** — 只做转发的包装层、只被调用一次的 helper → 内联。只有一个实现类的接口、只造一种产品的工厂、2–3 个字段的 builder、只有一种策略的策略模式、每个事件只有一个订阅者的事件总线、包着两个函数的 `XxxManager`/`XxxService` → 拆掉，直接用具体类型/函数。
_留_：当下有 **2 个以上真实使用方**的抽象；提供**可测试接缝**的抽象；框架强制的边界；代码库已经在用的模式。
_判据_：拿掉这层抽象后代码**更短且同样可读** → 它本来就不该在。

**命名** — 版本前后缀（`enhanced_`、`improved_`、`new_`、`_v2`、`final_`）→ 按"它是什么"命名，不按修订史命名。含糊动词（`processData`、`handleItem`、`doWork`）→ 命名真实的变换（`parseInvoiceRows`、`dedupeByEmail`）。生产代码里的占位名（`data`、`result`、`temp`）→ 改成它装的东西。（3 行函数里的 `i`、`acc` 没问题。）
> ⚠️ 只重命名本次冗余代码引入的符号。**改公开/导出符号的名字是 API 变更**——标出来，别动手。

**兼容层** — 崭新的代码上就写了"为了向后兼容"的转发别名、零调用方的废弃包装、项目根本不支持的版本的版本判断 → 全仓搜一遍确认没人用，然后删。**有人用 → 它不是冗余，留着。**

**测试** — 不可能失败的断言（刚构造完就 `assert x is not None`、`expect(true).toBe(true)`、断言 mock 返回了你 mock 给它的值）→ 改成真实的行为断言或删掉。过度 mock（每个协作者都被 mock 掉，测试什么都没验到）→ 只 mock 边界。断言私有方法被调了几次而不是断言可观测输出 → 改成行为断言。
> ⚠️ **铁律：绝不为了让测试套件变绿而删掉、跳过、削弱或 mock 掉一个失败的测试。** 这是最恶劣的一种冗余。

### 4.4 确定度分级

- **高**（可直接改）：正则就能识别的——调试语句、空 catch、占位文本、行尾空白。
- **中**（标出来等审）：结构性的——死代码、桩函数、没人用的基础设施。需要上下文。
- **低**（只报告）：启发式的——过度设计判断、辞藻膨胀。强依赖上下文。

自动修完"高"这一档之后跑测试；测试挂了就 `git restore .` 回滚。

### 4.5 绝不删的东西

- 信任边界上的校验与错误处理（没有对抗性回归测试就不许删）
- 解释**为什么**的注释、公开 API 签名、类型标注
- 通过反射/动态派发/字符串查表引用的代码
- 可达的"吞异常"逻辑（删了就是改行为——标出来，别动手）
- 范围之外的代码（报告它，别碰它）
- **清理过程中永远不许引入新的抽象或新的依赖**
- **切斯特顿的栅栏**：删一段看起来奇怪的代码之前先 `git blame`。**如果你说不清它为什么在那儿，你就还没有拿到删它的许可。**（例外：本次会话里你自己刚写的代码，来历你清楚。）

### 4.6 清理把东西弄坏了怎么办

1. 定位是哪一处改动导致的失败。
2. 回滚受影响的文件（或精确回退那个 hunk）。
3. 只把你能论证安全的那部分重新应用。
4. 重跑失败的那道关卡。
5. **同一个文件连续失败 3 次 → 停下来交给用户。** 不要继续闷头改。

## §5 审模式：只说删什么

评审时**只找过度设计**，一条发现一行：位置、删什么、用什么替代。**diff 最好的结局是变短。**

格式：`<文件>:L<行号>: <标签> <什么>。<替代方案>。`

| 标签 | 含义 |
| :--- | :--- |
| `delete:` | 死代码、没人用的灵活性、推测出来的功能。替代物：无。 |
| `stdlib:` | 手写了标准库自带的东西。点名那个函数。 |
| `native:` | 依赖或代码在做平台原生已有的事。点名那个特性。 |
| `yagni:` | 只有一个实现的抽象、没人设置的配置、只有一个调用方的层。 |
| `shrink:` | 同样的逻辑，更少的行。给出更短的写法。 |

❌ `这个 EmailValidator 类可能比必要的更复杂，你有没有考虑过现阶段是否需要所有这些校验规则？`

✅ `L12-38: stdlib: 27 行的校验类。判断 email 里有没有 "@" 就够了，1 行；真正的校验是那封确认邮件。`
✅ `L4: native: 为了一次格式化 import 了 moment.js。Intl.DateTimeFormat，0 依赖。`
✅ `repo.py:L88: yagni: AbstractRepository 只有一个实现。内联掉，等第二个实现出现再说。`

结尾给唯一重要的那个数字：`net: -<N> 行可删。` 没得删就说 `已经很精简，可以发。`

**边界**：只管过度设计与复杂度。**正确性 bug、安全漏洞、性能问题明确不在范围内**——它们该走常规评审，不要塞进这一趟。一个冒烟测试或一个 `assert` 自检是下限，不是冗余，永远不要把它列为可删项。**审模式只列清单，不动代码。**

## §6 输出与过程经济

- **先给代码。** 然后最多三行短说明：省掉了什么、什么时候该加回来。模式：`[代码] → 省掉了 X，等 Y 出现再加。`
- **说明比代码还长，就删说明。** 每一段为简化辩护的散文，都是把复杂度换成文字又走私回来了。（用户**明确要**的说明——报告、讲解、分阶段记录——照给不误，全须全尾；这条规矩只针对没人要的散文。）
- **别宣布你在用这个 skill**，别背诵"银行/阶梯/标签"这些内部词汇，别复述一遍需求，别为一个普通任务出风险矩阵。
- **任务清楚就直接动手。** 只在"答案会实质改变行为、安全或架构"时才提一个聚焦的问题。
- **只读、只搜、只改、只测能影响结果的东西。** 不要为了显得周全而调用工具。先跑最小的相关检查，有证据再扩大。
- **不要把算文件哈希当成每轮对话的收尾仪式。** 只在"字节一致性/完整性本身就是要验证的东西"、同步外部产物、或有意义的任务/发布检查点时才算哈希。任务进行中用聚焦的测试、diff 或 status 就够了。
- **不要写长计划**，除非用户要，或者任务确实是架构级的。
- 收尾报告保持简短：改了什么、验了什么、**以及还剩下哪些不寻常的兜底/兼容路径/重试/后台进程/额外状态，为什么留着**。

## §7 `SHORTCUT:` 债务标记

刻意的简化如果**切掉了一个有已知天花板的真实角**（全局锁、O(n²) 扫描、粗糙的启发式），就地留一条注释，写清天花板和升级路径：

```python
# SHORTCUT: 全局锁，吞吐量成为问题时改成按账户加锁
```

这条约定的意义是：**让"以后再说"不能悄悄变成"永远不做"**。需要盘点时全仓收割：

```bash
grep -rnE '(#|//|--) ?SHORTCUT:' . --exclude-dir={.git,node_modules,dist,build}
```

每条一行：`<文件>:<行号>，简化了什么。天花板：<写明的限制>。升级：<触发条件>。`
**没写升级触发条件的标记打上 `no-trigger` 标签**——烂在原地的就是这些。结尾：`共 N 条，其中 M 条没有触发条件。`

## §8 强度档位

默认 **standard**。用户可以点名切换。

| 档位 | 行为 |
| :--- | :--- |
| **lite** | 按要求建，但用一行点出更省的那个选项，让用户自己选。 |
| **standard** | 阶梯照跑。标准库和平台原生优先，最短 diff，最短说明。**默认。** |
| **ultra** | YAGNI 极端派。删优于加。先交一行版本，同一次回复里质疑需求本身。 |

例："给这些 API 响应加个缓存。"
- **lite**：加好了。顺带一提：`functools.lru_cache` 一行就能覆盖，你不一定要自己养一个缓存类。
- **standard**：在 fetch 函数上加了 `@lru_cache(maxsize=1000)`。省掉了自定义缓存类，等 lru_cache 明确不够用了再加。
- **ultra**：性能分析器没说要缓存之前先不缓存。真要缓存时用 `@lru_cache`。手写 TTL 缓存类是一个带命中率的 bug 农场。

## §9 收尾自检

交付前逐条对：

- [ ] **只改了被要求的东西。** 没有夹带没人要的抽象、没人要的文件、没人要的重构。
- [ ] 每一处防御机制都对应一个**真实的、能点名的**失败模式——不是我想象出来的。
- [ ] 新增的每样东西都答得上四问：**哪个当下的需求/调用方在用它？哪个观察到的故障、既有契约或可信风险需要它？为什么更简单的正确实现不够？人类维护者不用绕弯就能看懂吗？** 答不上 → 删掉、合并，或推迟。
- [ ] 没有 `_v2`/`_final`/`_NEW` 后缀的文件——变体活在 git 分支里。没有 git 已经提供的签名、哈希锁、完整性层。
- [ ] 错误会大声浮出来。没有沉默的兜底。
- [ ] 输入 → 处理 → 输出这条路径好追。命名清楚，控制流直接，报错诚实。
- [ ] 被替换掉的代码和孤儿代码已经删了（没有还在生效的兼容义务的话）。
- [ ] 非平凡逻辑留下了一个可运行的检查。**没有靠跳过、削弱、mock 把一个失败的检查改绿。**
- [ ] （删模式）动手前用绿灯测试锁过行为；没改公开 API 签名，没删类型标注；每一处删除都对得上 §4.3 里一个具名的类别——不是凭感觉。

## §10 什么时候不要用它

**这是刹车，不是方向盘。** 以下情况直接按对方要的做：

- 用户**明确**要一个防御性的、加固过的、生产级的系统。
- 任务确实是**安全攸关**的（医疗、航空航天、金融完整性）——按该领域的标准来。
- 用户在买一份正式审计或合规产物——就把那份产物做出来。
- 用户明确说了保留防御层、不要重构。

也不要拿它去删：**必要的复杂度**（真实的分布式协议、真实的密码学边界确实需要防御性代码——判据是"这份复杂度对应的是一个具名的真实需求，还是一个想象出来的需求"）、**领域复杂度**（ML 训练、数值计算、解析器本来就难，别压扁成一个"更简单"的错版本）、**团队约定**（仓库已有的既定模式跟着走，别引用这个 skill 把它拆了）。

目标不是"不惜代价的最少代码"，是**为自己付账的代码**——每一行都靠对应一个真实需求或一个真实故障模式来挣得它的位置。

拿不准就问一句："这里看着可以更简单——要我把防御层剥掉，还是这些加固是有意为之？"
