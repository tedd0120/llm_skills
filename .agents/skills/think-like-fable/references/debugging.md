# 调试排障（debugging）

> **何时在这里**：某个东西本该正常却出错了——报错、崩溃、结果不对、回归、"为什么会这样"。涵盖白盒（有源码）与黑盒（只能观察行为）。
> 区分线：从没工作过、要新做 → `implementation.md`；能跑但太慢 → `performance.md`；生产在烧、用户受影响 → 先 `ops.md` 止血，再回这里查根因。

## 崩点

**你第一个想到的原因几乎总是错的。** 调试的本质是**科学方法**：造出可复现的观察 → 提出可证伪的假设 → 用最小实验证伪 → 收敛到根因。两个头号杀手：(1) 没**稳定复现**就开始改代码——你在打一个看不见的靶子，"改一下看看"是在往伤口上撒随机数；(2) 修好**症状**却没碰**根因**，于是它换个地方、换个时间再犯。判断你到底修好没有，只有一条标准：**你能不能解释它为什么坏、为什么现在好了。**

## 框架（重心：勘察复现 + 谋划二分 + 验证根因）

- **框定** — 把模糊的"它坏了"变成精确的**期望 vs 实际**：确切输入、确切错误信息/堆栈、期望输出、实际输出。
  - 关键问题：什么时候开始的（新 bug 还是一直有）？哪个环境？100% 复现还是偶发？影响面多大？
  - · 判据：能写出一句"给定输入 X，期望 Y，实际 Z（附错误/堆栈）"。
- **勘察** — 建立**稳定的最小复现**，并读**地面真相**（真实日志、堆栈、变量值），而不是在脑内模拟代码。
  - 复现是一切的地基：不能复现，就先把"如何复现"当成当前要解的问题，别急着找因。
  - 偶发 bug：先找出让它**更容易复现**的条件（并发度、数据量、时序、特定输入、脏数据），把偶发逼成必现。
  - · 判据：有一组固定步骤能稳定触发；已亲眼看到真实失败现场（堆栈/日志/值），而非猜测。
- **谋划** — 用**二分**把搜索空间劈半，提出**可证伪的假设**。
  - 二分维度：代码历史（git bisect）、输入（删到最小仍复现）、调用链（在中点检查状态对不对）、环境/配置（逐个变量切换）。
  - 可证伪 = 设计一个能给假设"判死刑"的实验："如果是 A 导致的，那么屏蔽 A 后应不再复现"。
- **执行** — 一次**只动一个变量**跑实验，逐步逼近，直到定位到**根因那一处**；然后做**最小修复**，不顺手重构、不加功能（那会污染因果判断，是别的 play）。
- **验证** — 原复现步骤现在通过；**加一个先前会失败、现在通过的回归测试**（否则它一定回来）；确认没引入新问题。
  - · 判据：回归测试红转绿，且你能用一两句话解释根因与修复机理。
- **收尾** — 排查**同一根因的其他触发点**（同样的错常散落多处）；把反直觉的根因记档。

## 关键手法

- **git bisect**：已知"过去某版本好、现在坏"，就在提交历史里二分，O(log n) 次定位到引入 bug 的那次提交——比读 diff 猜快得多。
- **最小复现（MCVE）**：把触发 bug 的代码/输入删到"再删就不复现"，剩下的即根因裸露面；它顺带就是回归测试的种子。
- **二分定位**：在怀疑链路的中点插入检查（打印/断言/断点），问"到这里状态还对不对"，据答案把战场砍半，反复逼近。
- **打印 vs 断点**：想看时序演化、可复现 → 打印/日志；想深挖单点的对象状态 → 断点。核心都是去**看真实的值**，而不是假设它是什么。
- **橡皮鸭**：逐行向"人"讲这段为什么应该正确，矛盾往往在你替它辩护时自己蹦出来。
- **怀疑最近改动**：回归类 bug 的根因大概率藏在最近的 diff / 依赖升级 / 配置变更里，优先看那儿。
- **竞态/偶发**：怀疑共享可变状态、时序假设、外部依赖、脏数据；加日志记录时序，或人为放大并发/延迟来稳定复现。

## 反模式（含识别信号）

- ❌ 无复现就开改 — _信号：你在"改一下跑跑看"，一个来回动了好几处_ → ✅ 停手，先拿到稳定复现
- ❌ "好像好了"但说不清为什么 — _信号：你只知道"这么改就不报错了"，说不出根因_ → ✅ 继续查到能解释为止，否则你只是把 bug 藏深
- ❌ 一次改多处撞运气 — _信号：一个实验里同时动了多个变量_ → ✅ 回退到一次一个变量
- ❌ 修症状 — _信号：你在 catch 里吞异常、加 if 绕过、给现象打补丁_ → ✅ 沿调用链上溯到根因
- ❌ 相信注释/文档说的行为 — _信号：你在基于"这里应该是…"推理_ → ✅ 去看它真实是什么

## 走一遍（示例）

> 现象：用户报"导出 CSV 偶尔少最后一行"。
> **框定**：期望=导出 N 行，实际=偶尔 N−1 行；只在大文件出现，无稳定复现。
> **勘察**：猜测与数据量/时序相关，用 10 万行输入连跑 → 复现率升到必现，稳定了。看真实输出：少的**永远是最后一行**（这个细节是关键线索）。
> **谋划**：假设"缓冲区没 flush 就 close 了"。可证伪实验：close 前显式 flush，若不再丢行则假设成立。
> **执行**：定位到写完最后一批后直接 `close()`、未 `flush()`；改为先 flush 再 close（最小修复，不动其他）。
> **验证**：10 万行连跑 20 次，行数恒为 N；加一条"导出后校验行数"的回归测试，先在旧代码上确认它会红。
> **收尾**：全局搜同类"close 前未 flush"，发现日志模块也有一处，一并修。根因记档：缓冲写出必须 flush-then-close。

## 完成的定义

- [ ] 原复现步骤现在稳定通过
- [ ] 能用一两句话说清根因（而非"改了就好了"）
- [ ] 存在一个先前会失败、现在通过的回归测试
- [ ] 同一根因的其他潜在触发点已排查
- [ ] 未混入无关的重构 / 功能改动
