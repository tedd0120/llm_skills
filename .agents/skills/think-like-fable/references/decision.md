# 决策选型（decision）

> **何时在这里**：要在若干选项中**做出选择并给出推荐**——选技术栈/库/方案、该不该做某事、架构取舍、买还是自建。
> 区分线：**选项还没有、要先想出来** → `ideation.md`；选之前要先查资料 → `research.md`（二者常是上游）；已经定了要落地 → `implementation.md` / `planning.md`。

## 崩点

**好决策来自显式的判据加证据，而不是直觉或最响的声音。** 而在动脑之前要先问一个元问题：这是**可逆的（two-way door）还是不可逆的（one-way door）**？——它决定你该花多少功夫。把可逆的小决策当成天大的事反复纠结，和把不可逆的大决策草率拍板，是对称的两种浪费。此外还有两个隐性偏差：**沉没成本**（已投入的左右了"往后哪条更好"）和**新颖性偏好**（选时髦的而非合适的）。

## 框架（重心：框定可逆性 + 验证反驳）

- **框定** — 明确**要决定什么**、利害、约束、以及**可逆性**（单向门还是双向门）。不可逆的慎重、多收集证据；可逆的快决、试了再说。
  - · 判据：说得清"这个决定错了能不能轻易撤回、代价多大"。
- **勘察** — 列出**真实可选项**，**包括"不做/维持现状"**这个基线；为每项收集证据（可能先走一轮 `research.md`）。
  - · 判据：选项集完整，且有一个明确的"不做"基线。
- **谋划** — 定**判据与权重**，且判据要对齐**真实目标**（解决问题、总拥有成本、团队能维护），而非虚荣指标（star 数、时髦程度）。
- **执行** — 逐项按判据打分/对比；找出**致命缺陷**（deal-breaker：一个硬约束就能淘汰的项）快速砍掉。
- **验证** — **挑战自己的偏好**：如果被迫选另一个，我会怎么反驳现在这个？压测关键假设；检查是否被**沉没成本 / 新颖性 / 从众**带偏。
  - · 判据：能说出"什么证据/情况会让我改选"。
- **收尾** — 给**明确推荐** + 理由 + 关键权衡 + **在什么情况下应改选**。

## 关键手法

- **先分可逆性再定投入**：双向门（能低成本改回）的决策，别开长会——小成本试错胜过长时间纸上纠结；单向门（迁数据格式、公开 API、选核心框架）才值得重仓分析。
- **永远列"不做/现状"基线**：很多"该上什么方案"的正确答案其实是"先别上"——不设这个基线，你会被迫在几个都不够好的选项里硬选。
- **deal-breaker 先筛**：一个硬约束（License、合规、必须离线、团队无人会）能瞬间砍掉一半选项，比逐项打分快得多。
- **判据对齐真实目标**：写判据时问"这条真的服务目标吗"，剔掉"因为大厂在用"这种代理指标。
- **给一个明确选择**：把选项摆一桌不叫决策；要下判断、给推荐。罗列 = 把决策踢回给提问者。
- **写下"什么会让我改主意"**：让结论可被未来新证据推翻，而不是拍脑袋后死守——这也是对抗沉没成本的抓手。

## 反模式（含识别信号）

- ❌ 凭直觉/权威/谁声音大 — _信号：你说不出判据，只说"我觉得 X 更好"_ → ✅ 显式判据 + 证据
- ❌ 把可逆小决策当天大的事拖延 — _信号：一个能随时改回的选择你纠结了很久_ → ✅ 双向门快决试错
- ❌ 把不可逆决策草率拍板 — _信号：一个迁完难回头的事你几分钟就定了_ → ✅ 单向门加倍慎重
- ❌ 只罗列选项不给推荐 — _信号：你列了对比表却不说选哪个_ → ✅ 给明确选择 + 理由
- ❌ 只找支持预设的证据 — _信号：你没认真设想过"选另一个会怎样"_ → ✅ 主动反驳自己的首选

## 走一遍（示例）

> 决策："新对外 API 用 REST 还是 GraphQL？"
> **框定**：可逆性——中等偏可逆（初期可先上一种，后续能加另一种网关），所以别过度分析；利害=影响客户端接入体验与后端复杂度。
> **勘察**：选项 = REST / GraphQL / **先 REST 之后按需加 GraphQL（基线折中）**；各收集证据（团队经验、客户端形态、缓存需求、生态工具）。
> **谋划**：判据对齐真实目标——(1) 团队能否快速交付与维护，(2) 客户端取数是否高度多变，(3) 缓存/CDN 友好度，(4) 生态与调试工具。按重要性加权。
> **执行**：打分——团队熟 REST、客户端取数模式目前固定、需要 CDN 缓存（REST 占优）；GraphQL 的强项（客户端自由取数）当前场景用不上（接近 deal-breaker：为用不上的灵活性付复杂度）。
> **验证**：反驳自己——"如果选 REST，将来客户端变复杂怎么办？"→ 届时可加 GraphQL 网关，成本可控（印证可逆），故不构成翻案。检查没有被"GraphQL 更时髦"带偏。
> **收尾**：推荐**先 REST**；理由=匹配团队与当前取数模式、缓存友好、可逆；改选条件="当出现多个客户端且取数模式高度分化、REST 端点开始爆炸时，引入 GraphQL"。

## 完成的定义

- [ ] 判据显式且对齐真实目标（非虚荣指标）
- [ ] 选项集完整，含"不做/现状"基线，每项有证据
- [ ] 可逆性已评估，投入的谨慎程度与之匹配
- [ ] 给出了明确推荐 + 理由 + 关键权衡
- [ ] 写明了"什么证据/情况会让结论改变"
