# 部署运维（ops）

> **何时在这里**：动的是**活的、别人正在用的系统或环境**——上线/发布、搭建/配置环境、变更基础设施，或**线上事故响应**。
> 两个分支：**（a）计划性变更**（发布/搭环境/改配置）与 **（b）事故响应**（紧急，服务在烧）。下面分别标注。
> 区分线：定位代码缺陷本身 → `debugging.md`（事故止血后常要走它查根因）；一次性大版本迁移 → `migration.md`。修/回填**生产数据** → 本 play 的备份、小批量、可回滚，叠加 `automation.md` 的 dry-run 与幂等，双保险缺一不可。

## 崩点

**你动的东西有真实用户、爆炸半径大、且很多操作不可逆。** 两条铁律：
- **变更时**：可回滚地**小步推进**，并在**生产/近生产**验证真实行为——别信"本地没问题"。
- **事故时**：**先止血（stabilize），再查根因。** 用户在流血的时候钻研根因，是把优先级搞反了——先恢复服务，根因可以从容后置。

## 框架（重心：谋划可逆推进 + 验证真实/监控）

- **框定** — _变更_：明确目标状态、成功判据、**回滚条件**、影响面。_事故_：明确影响范围与优先级——**首要目标是恢复服务**。
  - · 判据：变更说得清"怎样算成功、出什么情况回滚"；事故说得清"谁受影响、恢复的标准是什么"。
- **勘察** — _变更_：摸清目标状态与当前差异、依赖、**前置检查（pre-flight）**。_事故_：快速定位影响范围与**最近的变更**（最近改动最可疑）。
  - · 判据：变更前置项已核对；事故的影响面与近期变更已掌握。
- **谋划** — _变更_：**可逆的小步推进**策略（金丝雀 / 蓝绿 / 灰度 / 特性开关）+ **回滚预案**。_事故_：选**最快的止血手段**（回滚 / 降级 / 扩容 / 关开关），根因后置。
- **执行** — _变更_：小步推进，**每步观察**再走下一步。_事故_：先止血恢复，**过程中把状态同步给受影响的人**（哪怕只是"已定位/处理中"），稳住后再从容查根因（转入 `debugging.md`）。
- **验证** — _变更_：在**生产/近生产**验证真实行为，**看监控指标**而非"看起来好了"。_事故_：确认服务确实恢复、且止血没引入新问题。
  - · 判据：监控指标（错误率/延迟/成功率）回到健康区间。
- **收尾** — _变更_：确认稳定、更新文档/runbook。_事故_：**无指责复盘（postmortem）**、补监控/告警**防复发**。

## 关键手法

- **先备份 / 先确保可回滚，再动手**：不可逆操作（删数据、改生产配置）前，先有退路——快照、备份、或一键回滚的版本。
- **金丝雀 / 灰度先行**：新版本先放 1% 流量 → 观察监控 → 逐档放量；出问题只影响一小撮且能秒切回。
- **改一处、看一处**：批量盲改是运维事故的头号来源；一次一个变更、观察确认，再下一个。
- **监控为准，不靠感觉**：部署完盯错误率/延迟/资源/业务指标曲线，而不是"点一下首页能开"就宣布成功。
- **事故先恢复后查因**：回滚到"上一个已知良好状态"往往是最快的止血；根因等服务稳了再从容查。
- **最近变更优先怀疑**：事故的原因大概率是最近一次部署/配置/依赖改动，先看那儿。
- **生产操作二次确认 + 基础设施即代码**：不可逆命令前停一秒确认对象/范围/退路；能用 IaC/脚本就别手工点，保证可复现、可评审、可回滚。

## 反模式（含识别信号）

- ❌ 大范围一次性变更 — _信号：一次就把新版本推给 100% 流量_ → ✅ 金丝雀/灰度、可回滚小步
- ❌ 无回滚预案就上线 — _信号：你答不出"上线后发现不对怎么秒退"_ → ✅ 先备份 + 回滚路径就绪
- ❌ 事故时急着钻研根因 — _信号：用户在报错，你却在读代码找根因_ → ✅ 先止血恢复，根因后置
- ❌ "看起来好了"就收工 — _信号：你没看监控就宣布成功_ → ✅ 以监控指标为准
- ❌ 手工不可复现的生产操作 — _信号：靠记忆手敲一串生产命令_ → ✅ IaC/脚本化 + 二次确认

## 走一遍（示例）

> **变更分支**——任务：发布订单服务新版本。
> **框定**：成功=错误率与延迟不劣化、订单功能正常；回滚条件=错误率超基线 2 倍或延迟 p95 超阈值。
> **勘察**：pre-flight——确认数据库迁移脚本已就绪且可回滚、特性开关到位、回滚版本可一键切、监控面板打开。
> **谋划**：金丝雀策略——先 5% 流量，观察 10 分钟，再 25% → 50% → 100%；每档都能秒切回旧版本。
> **执行**：切 5% → 盯监控。发现新版本错误率轻微上升、日志指向一个空指针 → **不硬扛**，立即切回旧版本止血（可逆小步的价值）。
> **验证**：切回后错误率回落到基线（监控确认，而非感觉）；用户无感。
> **收尾**：错误留到测试环境走 `debugging.md` 复现修复，修好再重走灰度；给这个空指针场景补监控告警。
>
> **事故分支**（简例）：线上 5xx 突然飙升 → 先看最近变更，30 分钟前刚发过版 → **先回滚上个版本止血**，确认 5xx 回落、服务恢复 → 再从容走 `debugging.md` 查根因 → 无指责复盘、补一条"发版后错误率自动告警"防复发。

## 完成的定义

- [ ] _变更_：目标状态达成且在生产/近生产验证，监控指标健康
- [ ] _变更_：回滚路径就绪且已确认可用，文档/runbook 更新
- [ ] _事故_：服务已恢复（监控回到健康区间），止血未引入新问题
- [ ] _事故_：根因已定位、防复发措施（监控/告警/修复）落地
- [ ] _事故_：无指责复盘完成
