# 评审（review）

> **何时在这里**：评估**别人（或你自己）已产出的东西**——审代码、评方案、挑毛病、给反馈。产物是一份**分级的发现清单**。
> 区分线：要自己找 bug 并修 → `debugging.md`；要在方案间选一个 → `decision.md`；要理解它怎么工作（不评判）→ `comprehension.md`。

## 崩点

**先查正确性，再谈品味。** 两个杀手：**纠结在命名/风格上，却漏掉了会导致数据丢失的致命 bug**；以及**堆一大坨不分级的意见**，让作者分不清哪条是"必须改"、哪条是"顺嘴一提"，于是要么全盘照收、要么全盘无视。评审的价值密度取决于两点：把注意力放在**最会出事**的地方，以及把结论**排好序**。还有一个信任杀手：**误报**——没验证就断言是 bug，几次之后你的评审就没人当真了。

## 框架（重心：谋划分层 + 验证误报）

- **框定** — 明确评审对象、**作者的意图**（他想达成什么）、验收标准、以及本次评审的重点（正确性 / 安全 / 性能 / 可维护）。
  - · 判据：说得清"这段改动想干什么、我重点看什么"。
- **勘察** — 读懂改动的意图与上下文；必要时**跑/读**以理解真实行为，而非只看 diff 表面的几行。
  - · 判据：理解了改动如何融入整体，而非孤立看几行。
- **谋划** — **分层过，按严重度排序**：先**正确性与安全**（会不会坏、有没有漏洞、会不会丢数据/串数据），再**性能**，最后**可维护性/风格**。
- **执行** — 逐项检查。每条 finding 附：**位置** + **为什么是问题** + **具体失败场景**（什么输入/状态会触发）+ **建议**。
- **验证** — 每条 finding 自检：**这真会发生吗？有没有反例让它其实没问题？**——先排除**误报**再提出。然后按严重度排序。
  - · 判据：每条保留的 finding 都有一个具体、可信的失败场景。
- **收尾** — 结论 = **分级清单**（阻断 / 重要 / 次要 / 建议），具体、可执行、对事不对人；也指出做得好的地方。

## 关键手法

- **先问"最坏会怎样"**：过每段改动时先想安全与正确性——能不能造成数据丢失、串号、越权、钱算错、死循环。这些永远排在风格前面。
- **给可复现的失败输入**：不说"这里可能有问题"，而说"当 userId 为空时第 N 行会拿到别人的缓存"——具体到触发条件，作者才能验证与修。
- **分清"必须改"与"个人偏好"**：明确打标签；把个人风格偏好压到最低优先级，别让它淹没关键问题。
- **误报自检**：提出前先自己找一个"其实没问题"的反例；找不到反例，才是真 finding。
- **引用具体行号/位置**：让作者一键定位，别让他猜你说哪儿。
- **肯定亮点**：指出做得好的地方——评审是校准而非找茬，正向信号同样有价值。
- **对事不对人**：评的是代码/方案，措辞针对代码而非作者。

## 反模式（含识别信号）

- ❌ 纠结风格漏掉致命 bug — _信号：你的评论全是命名/格式，没碰逻辑正确性_ → ✅ 正确性与安全优先
- ❌ 一大坨不分级的意见 — _信号：20 条评论平铺、没轻重_ → ✅ 按严重度分级（阻断/重要/次要/建议）
- ❌ 泛泛"这里不好" — _信号：你说了"感觉不对"但给不出触发场景_ → ✅ 给具体失败场景 + 建议
- ❌ 没验证就断言是 bug（误报）— _信号：你没想过反例就下了"这会崩"的结论_ → ✅ 先找反例确认再提
- ❌ 人身化措辞 — _信号：评论在说"你怎么又…"_ → ✅ 对事不对人

## 走一遍（示例）

> 对象：一个 PR——"给用户资料接口加缓存以降延迟"。
> **框定**：作者意图=降延迟；重点看正确性（缓存最易出正确性 bug）与安全。
> **勘察**：读懂改动——它用 `profile:{路径}` 作缓存 key，缓存用户资料响应。跟一次真实请求看 key 怎么拼。
> **谋划 + 执行**：分层过——
> - **正确性/安全（阻断）**：缓存 key 只含路径、**不含 userId**，而该接口按登录态返回"当前用户"资料 → 失败场景：用户 A 请求后，用户 B 命中 A 的缓存，**串号泄露他人资料**。附行号 + 建议：key 纳入 userId。
> - **正确性（重要）**：资料更新后没有失效缓存 → 失败场景：改完昵称，一分钟内仍显示旧的。建议：更新时删除对应 key。
> - **性能（次要）**：TTL 设了 24h 偏长，命中率与新鲜度权衡建议缩短。
> - **风格（建议）**：常量魔法值 86400 建议命名。
> **验证**：逐条找反例——串号那条，确认接口确实按登录态返回、key 确实不含 userId，成立（非误报）；失效那条同样成立。
> **收尾**：按"阻断/重要/次要/建议"排好，肯定"加缓存方向对、降延迟思路好"，措辞对事不对人。

- [ ] 每条 finding 有位置 + 具体失败场景 + 建议
- [ ] 发现已按严重度分级（阻断/重要/次要/建议）
- [ ] 误报已通过反例自检排除
