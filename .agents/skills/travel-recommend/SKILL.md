# 旅游目的地推荐 Skill

你正在执行一次旅游目的地推荐任务。最终产出一份**总推荐清单**（README.md，按综合评分排序，每行可点击跳转）+ 各目的地的**详情报告**（每个一份 `{地名}.md`）。

## 架构总览

信息引擎分两路：

- **硬信息路（并行）**：气候、机票/酒店参考价位、消费水平、安全性 —— 用 Tavily MCP（`mcp__tavily-mcp__tavily_search` / `mcp__tavily-mcp__tavily_research`）+ 天气 API 查询，3-5 个目的地**同时**派出子 agent。
- **软信息路（串行）**：美食、玩法特色、避坑体验 —— 以**小红书为主引擎**。由于小红书依赖单一登录态与浏览器自动化，**必须逐个串行调用**，不可并行。
- **融合**：两路信息汇合 → 按 [scoring.md](scoring.md) 的 6 维加权评分 → 写报告。

**关于小红书的调用方式（核心要求）**：不调用 `xiaohongshu-scraper` skill 本身（它有强制用户澄清，无法静默）。本 skill **直接驱动其底层资产**——登录脚本 + fetch/summarize/formatter 三个子 skill，所有参数在下方阶段四里定死，对用户全程静默（仅首次需扫码登录一次，之后复用 cookie）。

## 输出目录约定（核心要求）

**所有运行产物必须写入仓库根目录下的 `data/`，禁止写入 `.agents/skills/` 任何 skill 目录。**

```
旅游最终报告目录：
  TRAVEL_OUTPUT_DIR = <仓库根目录绝对路径>/data/travel-recommend/YYYYMMDD_HHmmSS_主题/
    ├── README.md              # 总推荐清单
    ├── tasks.md               # 执行任务清单
    ├── {地名1}.md             # 各地详情
    ├── {地名2}.md
    └── ...

小红书抓取产物目录（每个目的地独立一个，沿用 xiaohongshu 约定）：
  <仓库根目录绝对路径>/data/xiaohongshu/YYYYMMDD_HHmmSS_{地名}/
    ├── raw.json
    ├── {地名}.md              # 小红书报告（被读取后融合进详情页）
    └── id_url_map.json        # 开启超链接时
```

- 传给任何脚本或子 skill 的路径**必须使用绝对路径**（脚本按 cwd 解析相对路径，容易走错）
- 时间戳必须使用当前系统时间，禁止使用示例或模板时间
- 主题名由你根据用户的时间段+出发地+偏好概括（如 `7月中旬上海亲子游`）
- **防目录碰撞**：小红书目录的主题段直接用明确地名（如 `..._杭州`、`..._苏州`），不靠秒级时间戳区分

## 阶段一：澄清（1 轮，必须执行）

目标：一次性收齐出游参数。**只问这一轮，缺字段用默认兜底，不阻塞。**

### ⚠️ 固定模板（强锁定，禁止改写）

向用户发送的澄清消息**必须与下方模板逐字一致**。下方代码块内的全部内容（标题、emoji、字段顺序、措辞、括号内的示例文字、空行）均为固定文本，**整体复制粘贴发送**。

**禁止行为**（违反即视为 bug）：
- ❌ 自行加问候语或开场白（如"您好""很高兴帮您规划"）
- ❌ 改写任何措辞或字段名（如把"预算"改成"花费""预算档位"）
- ❌ 替换、增删 emoji
- ❌ 增删字段、调整字段顺序
- ❌ 把模板"合并"成一段话、改成表格或其他形式
- ❌ 翻译成其他语言或改繁简体
- ❌ 自行填入用户已提过的信息（模板里的占位/示例文字保持原样，由用户在回复时填）

**唯一允许的偏离**：用户的触发消息里**已经明确给出**了某字段（如直接写了时间段+出发城市+目的地范围），可跳过这一轮澄清直接进阶段二；此时无需发送本模板。

### 模板正文（复制此代码块内容发送）

> ⚠️ **各字段之间的空行不可删**：终端按 GitHub-flavored markdown 渲染，字段间若只有单换行会被当成同一段落、挤成一行。必须保留**空行**让每个字段独立成段，才能一行一字段地展示。整理排版时切勿删除这些空行。

```markdown
请确认出游参数（括号内为默认值，可直接回复"全默认"或只填你想改的项）：

📅 时间段：（必填，如"7月中旬，约5天"）

📍 出发城市：（必填，如"上海"）

💰 预算：（默认：中等，可选 节俭/中等/宽裕）

👥 同行人：（默认：2大人，可补充 亲子/老人/独自/朋友团 等）

🏷️ 偏好标签：（默认：综合，可选 海岛/古镇/自然/美食/人文/亲子/徒步/购物…，可多选）

🗺️ 目的地范围：（默认：AI 发散，可填"江浙沪""东南亚""日本""任意"等）

🌐 是否含出境：（默认：否，即国内）

补充说明（可选）：__________
```

### 处理规则（内部逻辑，不展示给用户）

- 时间段和出发城市为必填，用户未提供则**只追问这两项**（追问消息也用最简形式，不重发整份模板），其余缺失一律用默认
- 用户回复"全默认"或类似表达 → 除时间段/出发城市外全用默认（这两项仍需用户提供）
- 用户给了时间段/出发城市但没回其他项 → 视为用默认

### 澄清完成标志

用户提供了时间段 + 出发城市（无论是否回复其他项）。完成后**立即**：
1. 创建 TRAVEL_OUTPUT_DIR（绝对路径，带当前时间戳）
2. 写入 tasks.md（见下方任务清单）

## 阶段二：候选产生与轻筛

### 1. 产生候选池（5-10 个）

- **用户给了范围**（如"江浙沪""东南亚"）→ 在范围内枚举具体目的地
- **用户让 AI 发散**（默认）→ 依据三个硬约束发散：
  - **时段适配**：该月份/季节的气候与季节性景观（盛夏避暑往高纬度/高原，冬季避寒往南，雨季避开海岛等）
  - **出发地可达性**：从出发地直飞 ≤4h 或高铁 ≤6h 优先（出境按飞行圈，遵循用户"是否含出境"设定）
  - **偏好匹配**：与用户偏好标签呼应（亲子→主题乐园/海滩；文艺→古镇/博物馆；自然→山岳/湖泊）

### 2. 接地校验（核心要求，禁幻觉）

每个候选**必须**用 Tavily MCP（`mcp__tavily-mcp__tavily_search`）校验：确认是**真实存在的旅游目的地**且**该时段确实开放可去**。校验失败（虚构地名、该时段封山/不开放、根本到不了）一律剔除。**禁止把未经校验的地名写进候选池。**

### 3. 轻筛

对校验通过的候选做一次轻量评估，剔除明显硬伤：
- 该时段气候极端（台风季海岛、火炉季户外城市、严寒无室内项目）
- 签证/通行证难办（出境类，与用户"是否含出境"冲突的）
- 该时段无核心看点（如枯水期的瀑布、非花期的花海）

**保留规则**：留 **3-5 个**进入深度调研，**额外保留 1-2 个备选**（阶段五某地信息严重不足时顺位补上）。把候选清单写入 `TRAVEL_OUTPUT_DIR/candidates.md`。

## 阶段三：并行查硬信息

对 3-5 个候选目的地，**在一条消息里同时派出多个子 agent**（每个目的地一个），并行查询硬信息。每个子 agent 的任务：

> 调研 `{目的地}` 在 `{时间段}` 的以下信息，返回结构化摘要。
>
> 使用 Tavily MCP（`mcp__tavily-mcp__tavily_search` / `mcp__tavily-mcp__tavily_research`）和天气 API：
> - **气候**：该时段气温区间、降水量、极端天气风险、穿衣建议。优先用 `curl -s "https://wttr.in/{城市英文名}?format=j1"` 或 `https://wttr.in/{城市名}` 获取结构化天气，再用 Tavily MCP 补充季节性描述
> - **机票参考价位**：从 `{出发城市}` 到 `{目的地}` 的交通方式（直飞/中转/高铁）、单程参考价位**区间**（如"800-1500元"）。用 Tavily MCP 搜"出发城市 目的地 机票 价格"或携程/去哪儿公开页。抓不到精确价就报区间并标注"参考价位"
> - **酒店参考价位**：该地住宿参考价位区间（经济型/中档/高档各一档），用 Tavily MCP 搜
> - **消费水平**：当地人均/天的餐饮+交通+门票参考
> - **安全性**：治安状况、常见骗局、季节性自然风险。用 Tavily MCP 搜"`目的地 避坑`""`目的地 旅游 安全`"
>
> 返回格式：
> ```
> ## {目的地} 硬信息摘要
> ### 🌤️ 气候
> ### ✈️ 交通与参考价位
> ### 🏨 住宿参考
> ### 💰 消费水平
> ### ⚠️ 安全性
> ### 📚 来源
> ```

**完成标志**：收到所有目的地的硬信息摘要。每份摘要保存到 `TRAVEL_OUTPUT_DIR/hard_info_{地名}.md`。

## 阶段四：串行查软信息（小红书，逐个目的地）

**对每个候选目的地，依次**（不并行，因小红书依赖单一登录态）复刻以下流程。所有参数按本阶段定死，对用户静默。

### 步骤 1：为该目的地创建独立目录

```
XHS_OUTPUT_DIR = <仓库根目录绝对路径>/data/xiaohongshu/YYYYMMDD_HHmmSS_{地名}/
```
（绝对路径，主题段用地名，确保各目的地目录不碰撞）

### 步骤 2：登录（仅首次需用户扫码，之后复用 cookie）

```text
python .agents/skills/xiaohongshu-scraper/scripts/orchestrate_login.py \
  --poll-interval 2 \
  --output-dir <XHS_OUTPUT_DIR 绝对路径>
```

监听输出：
- 出现 `NEED_LOGIN:<abs_path>` 或对应 LOGIN_EVENT → 向用户发送"请扫码登录小红书。二维码文件：`<abs_path>`"（**仅首次**，cookie 持久化后后续目的地自动复用）
- 出现 `LOGIN_OK`/`LOGIN_SUCCESS` → 继续
- 出现 `LOGIN_TIMEOUT`/`LOGIN_FAILED`/`ORCHESTRATOR_ERROR` → **降级处理**（见下方）

### 步骤 3：抓取 → 调用 xiaohongshu-fetch skill

阅读 `xiaohongshu-fetch` 的 SKILL.md，用以下**定死参数**调用：

| 参数 | 取值 |
|------|------|
| `OUTPUT_DIR` | 上面的 XHS_OUTPUT_DIR（绝对路径） |
| `--keywords` | `"{地名}旅游攻略,{地名}美食,{地名}避坑"` |
| `--max-posts` | `40` |
| `--search-strategy`（JSON） | `[{"keyword":"{地名}旅游攻略","posts_count":20,"intent":"获取整体推荐与玩法"},{"keyword":"{地名}美食","posts_count":12,"intent":"特色美食与餐厅"},{"keyword":"{地名}避坑","posts_count":8,"intent":"避坑与安全提示"}]` |
| `--hyperlinks` | 传（开启，报告里链接可点） |
| 速度模式 | **不传** `--speed-mode` 也**不传** `--safe-mode`（即正常模式，平衡速度与风控） |

输出 `{XHS_OUTPUT_DIR}/raw.json`（+ `id_url_map.json`）。

### 步骤 4：生成报告 → 调用 xiaohongshu-summarize skill

阅读其 SKILL.md，传 `OUTPUT_DIR` + `REPORT_FILE={XHS_OUTPUT_DIR}/{地名}.md`，读取 raw.json 生成报告。

### 步骤 5：格式化 → 调用 xiaohongshu-formatter skill

阅读其 SKILL.md，传 `REPORT_FILE={XHS_OUTPUT_DIR}/{地名}.md`，原地覆盖增强 emoji + 替换超链接。

### 降级处理（核心要求）

任一步骤出现以下情况 → **该目的地软信息改用 Tavily MCP 兜底**，不中止整体流程：
- 登录失败/超时/被风控
- fetch 报错或抓取数据为空
- summarize/formatter 失败

降级行为：用 Tavily MCP（`mcp__tavily-mcp__tavily_search`）搜 `"{地名}旅游攻略""{地名}美食推荐""{地名}避坑"`，整理出美食/玩法/避坑摘要。在该目的地详情页顶部标注 `> ⚠️ 小红书数据缺失，软信息为通用搜索结果，鲜活度较低`。

## 阶段六：校验与发送

### 1. 任务清单校验（核心要求）

阶段一创建 TRAVEL_OUTPUT_DIR 后立即写入 `TRAVEL_OUTPUT_DIR/tasks.md`：

```markdown
## 执行任务清单

- [ ] 澄清出游参数
- [ ] 候选产生与轻筛
- [ ] 并行查硬信息
- [ ] 串行查软信息（小红书）
- [ ] 融合打分与写报告
- [ ] 校验与发送
```

**每完成一项立即将 `[ ]` 改为 `[x]`**。阶段六发送前**必须**执行：

```text
python .agents/skills/travel-recommend/scripts/verify_tasks.py <TRAVEL_OUTPUT_DIR>/tasks.md
```

返回 `TASKS_INCOMPLETE` → **报错中止，禁止发送未完成的报告**。

### 2. 发送

- 将 README.md 内容发送到对话（总清单）
- 告知用户详情文件路径：`TRAVEL_OUTPUT_DIR/{地名}.md`
- 如有降级，在发送时一并提示哪些目的地存在数据缺口

## 降级处理总表

| 故障点 | 降级行为 | 详情页标注 |
|:------|:---------|:----------|
| 小红书登录失败/超时/被风控 | 该地软信息改用 Tavily MCP 搜攻略/美食/避坑 | `⚠️ 小红书数据缺失，软信息为通用搜索结果` |
| 机票/酒店价抓不到 | 报**参考价位区间**而非精确价，来源用 Tavily MCP 估 | 标注"参考价位" |
| 某目的地总信息严重不足 | 从候选池**顺位补**一个备选（备选也跑阶段三/四） | 在 README 候选说明里注明替换 |
| Tavily MCP 整体不可用 | 退化为纯小红书模式（软信息为主，硬信息用小红书相关帖近似） | `⚠️ 硬信息为估算` |

**核心原则：永远要出一份报告，宁降级不中止。** 每次降级在详情页顶部用 `⚠️` 标注数据缺口。
